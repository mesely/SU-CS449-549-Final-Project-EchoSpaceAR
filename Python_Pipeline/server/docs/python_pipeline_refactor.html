EchoSpaceAR • Unity + Python • Audio Architecture

From raw sound to live environmental guidance.

EchoSpaceAR is a two-sided audio system. Unity captures sound and presents the user experience, while the Python server performs live signal analysis, sound classification, speech transcription, and event packaging. This page maps the full route clearly, from microphone frames to user-facing cues.

Primary runtime path

Unity sends float32 PCM chunks to the Python bridge. The server fans the same stream into multiple workers, then returns structured events that Unity can poll and render as accessible cues.

Operational Flow

Step-by-step runtime sequence

Each lane consumes the same incoming audio, but they operate with different window sizes and goals. That separation is what makes the system responsive while still producing richer context.

1

Client hello

Unity opens a session and identifies itself so audio can start flowing into the backend.

2

Chunk upload

Audio arrives as base64-encoded float32 PCM and is decoded back into a mono numpy stream.

3

Queue fan-out

The visualizer distributes the same chunk to SPL plotting, YAMNet inference, and STT buffering.

4

Sound detection

YAMNet builds rolling windows and emits top labels such as speech, siren, horn, music, or glass break.

5

Speech decoding

Whisper uses a speech gate and pre-roll so transcripts are generated only when spoken content is likely present.

6

Context delivery

Gemini can summarize recent sound and speech windows, and Unity polls those events to inform the user.

Python Runtime

Detailed view of the Python pipeline

The Python side is intentionally split into dedicated lanes. Each lane owns one kind of processing, but they all coordinate through the visualizer and the HTTP event bridge.

Ingestion Lane

The bridge receives Unity chunks, decodes them, normalizes them into mono float32 arrays, and forwards them to the registered sink.

  • Session-aware event storage
  • Audio sink registration for Unity mode
  • Shared entry point into the runtime queues

Signal Lane

The visualizer computes RMS dBFS continuously for the live matplotlib view and keeps short rolling histories for the UI.

  • Low-latency level updates
  • Device selection and sample-rate handling
  • Window assembly for downstream workers

Recognition Lane

YAMNet classifies acoustic context, while Whisper activates only when speech probability is strong enough to justify transcription.

  • Reduced-label or full YAMNet support
  • Speech gating with hysteresis
  • Pre-roll buffering to preserve utterance starts

Interpretation Lane

Gemini receives compact windows of recent STT text and classifier events, then produces short environment summaries and alerts.

  • Window-based prompt building
  • JSON-only output parsing
  • Summary and important-event packaging
Timeline View

How the windows overlap in time

Not every subsystem reacts on the same cadence. This staggered structure allows fast sound feedback, slightly slower speech decoding, and broader context summaries without blocking the stream.

Folder Guide

What the major folders are responsible for

These folders represent the system in layers: Unity experiences at the edge, shared audio analysis in Python, and runtime assets plus generated outputs around that core.

Android

Unity client

The Android Unity project packages the mobile-facing experience. It is responsible for capture, transport, and how detected events are presented on a phone or tablet.

  • Gameplay and UI scene logic
  • Microphone input on Android hardware
  • Networking calls to the Python backend

Quest2_3

Unity XR client

The Meta Quest project contains the immersive side of the product. It can consume the same backend event stream while placing cues inside a spatial interface.

  • XR scenes and interaction flow
  • Quest-specific deployment assets
  • Accessibility feedback inside VR/AR

Python_Pipeline/server

Analysis backend

This is the runtime center of the project. It receives audio from Unity, coordinates analysis workers, stores logs, and exposes event endpoints.

  • HTTP bridge and event store
  • Live audio analysis runtime
  • Models, logs, and developer docs

pipeline_runtime

Core package

The internal Python package separates configuration, device utilities, model integrations, helper functions, and the visualizer orchestration layer.

  • Cleaner ownership per module
  • Shorter files for faster navigation
  • Shared helpers used across runtime lanes

models + reduced_yamnet_savedmodel

Model assets

This area holds the reduced YAMNet label metadata and the exported SavedModel/TFLite artifacts used by the classifier lane.

  • Reduced label mapping
  • SavedModel export output
  • Lightweight deployment-friendly assets

docs + logs

Support material

The docs folder explains the architecture for humans, while the logs folder captures classifications, transcripts, and LLM summaries for debugging and evaluation.

  • Architecture reference page
  • CSV and JSONL outputs
  • Observation trail for testing runs
Key Files

Important files inside the Python server

These files form the practical backbone of the runtime. Together they make the server easier to read, easier to maintain, and easier to explain to someone new joining the project.

Pipeline.py

The stable entry script. It delegates startup into the runtime package so existing launch commands remain simple.

pipeline_http_bridge.py

Owns the Unity-facing HTTP endpoints, session event storage, chunk decoding, and event retrieval flow.

config.py

Collects environment loading, runtime constants, feature toggles, directory paths, and optional dependency detection.

visualizer.py

The orchestration hub. It manages queues, the SPL graph, classifier windows, STT publishing, and optional summary windows.

classification.py + build_reduced_yamnet.py

One file loads the runtime classifier, while the other creates the reduced YAMNet model and label mapping used by deployment.

transcription.py + llm.py

These handle language-aware layers: rolling Whisper transcription and compact Gemini interpretation windows.

Outputs

What the pipeline emits back into the system

The backend is not just a classifier. It produces several event shapes that Unity can combine into accessible, contextual feedback.

YAMNet events

Top labels, dominant class, confidence, and SPL information for the analyzed window.

STT events

Transcribed speech segments with effective window length, language, and timestamps.

LLM events

Short environment summaries and user messages built from recent sound and speech context.
